关于Session、cookie、token

Created2026-09-18|漏洞复刻知识补充
|Post Views:

概念

首先要搞懂http这个协议的缺陷的地方。首先HTTP协议是一种无状态的协议，所谓的无状态就是客户端每次想要链接客户端通信的时候，都需要重新进行连接，这意味着请求一次客户端和服务器连接一次，下一次请求与上一次请求是没有任何关系的。

这种无状态的方式就存在一个问题：如果判断两次请求的是同一个人呢？就好比用户在页面A发起请求个人信息，然后再另一个页面同样发起请求获取个人信息，我们如何确定这两个请求是同一个人发送的呢?

为了解决这个问题，我们就波切需要一种方式知道发起请求的客户端是谁？此时，cookie、token、session就出现了，他们可以解决客户端表示的问题，在扩大一点就是解决权限问题。

简单来说就是这三样东西相当于用户的身份证，让服务器知道是谁发送的请求。

什么是cookie？

简单来说，它是一种在客户端存储数据的技术，由服务器发送给客户端的小型文本，存储在客户端的浏览器当中，限制大小为4KB左右。在客户端发送时，浏览器会自动将相应的Cookie信息发送给服务器，让服务器知道你是谁，Cookie可以存储用户的登录状态、购物车信息。

简要：

  • Cookie有存储大小限制，4KB左右。

  • 浏览器每次请求都会携带cookie在请求头中。

  • 字符编码为Unicode，不支持直接存储中文。

  • 数据可以被轻易看到。

所以现在因为有了更多的存储方案出现逐渐被取代。

cookie的主要属性：

大体流程：

  1. 客户端发送登录请求

  2. 服务器接收到请求之后生成一个session会话。

  3. 服务器响应客户端，并在响应中设置set-cookie。cookie中包含了sessionid，他的格式如下：Set-Cookie：value[;expires=date][;domain=domain][;path=path][;secure]。其中sessionid是用来标识客户端的，类似于你去饭店里，服务员给你一个号牌，后续上菜的时候根据这个号牌找到在哪里。

  4. 客户端接收到请求后，如果服务器给了Set-Cookie，那么下次浏览器就会在请求头中自动携带cookie。

  5. 客户端发送其他请求，自动携带了cookie，cookie中携带有用户信息等。

  6. 服务端接收请求，验证cookie信息，比如通过sessionid来判断是否存在会话，存在则正常响应。

总结：额，我个人对于cookie的概念的话就是他是一个用来标示用户的身份的东西，其中包含了sessionid会话id，这个id能够存放客户端的相应的用户信息，这类似于一种牌号，这个牌号是服务器给的，当我们第一次请求登录的时候得到这个牌号，之后会自动存放在浏览器中，之后访问的时候会在请求头中带有这个牌号对么？

cookie主要特点

  1. cookie存储在客户端

  2. cookie不可跨域，但是如果设置了domain，那么他们是可以在一级域名和二级域名之间共享。

什么是session？

服务器创建session还有与之对应的sessionid，然后通过响应发送给客户端，存储在cookie中。当客户端访问同一个网页的时候携带这个session，服务器判断客户端发送来的请求，检查sessionid如果有那么正常处理这个请求。如果没有则会新生成一个sessionid与session对应，然后响应时将sessionid给客户端。

每一个客户端与服务器连接，服务端都会为该客户端创建一个session，并将session的唯一标识sessionid通过设置Set-Cookie头的方式发送给客户端，客户端将sessionid存储在cookie中。

与cookie的区别

cookie和session，他们两者之间的关系是通过sessioid关联的，所以总结来说sessionid是cookie和session之间的桥梁。

session是基于cookie开发的，他们两个主要有以下特点：

  1. session比cookie更加安全，因为他们是在服务端的，cookie是存在客户端的。

  2. cookie只支持存储字符串数据，session支持存储任意数据。

  3. cookie的有效期可以设置较长时间，session有效期都比较短。

  4. session存储空间大，cookie有限制。

系统需要实现鉴权，可以单独使用cookie也可以单独使用session，但是建议两者结合使用。

token是什么

概念

Token是一种在客户端和服务端之间传递身份信息的方式。当用户登录成功之后，服务端会生成一个Token，将其发送给客户端。客户端在后续的请求中，需要将Token携带在请求头或者请求参数中。服务端通过验证Token的合法性，就可以确定该请求来自哪个用户，并且可以根据用户的权限的权限进行相应的操作。Token可以有效避免了Cookie的一些安全问题，比如CSRF攻击。

详细了解：RFC 7519 - JSON Web 令牌 （JWT）

比喻这一块：

  • ​Cookie/Session​：你的 Cookie（Session ID）像是一张“会员卡号”，服务器需要根据这个卡号去后台的数据库（Session 存储）里查询你的完整会员信息（包括权限）。

  • ​Token​：你的 Token 本身就像一张“防伪工作证”，工作证上直接印着你的姓名、工号、部门、权限等级​（这些就是 Token 的 Payload 部分）。门口保安（服务器）不需要打电话回人事部查档案，只需要用特定方法（验证签名）检查一下这个工作证是不是公司颁发的、有没有被涂改，然后直接看证上的信息就知道你能不能进入这栋大楼（访问这个接口）。

token的组成

Token是一个由一串字符组成的令牌，用于计算机系统中进行身份验证和授权。它通常用于三个部分组成：标头、有效载荷、前面。

  1. 标头（Header）：包含了算法和类型，用于指定如何对有效载荷进行编码和签名。常用的算法有HMAC、RSA、SHA等。

  2. 有效载荷（Payload）：包含了一些信息，如用户ID、角色、权限等，用于验证身份和授权。有效载荷可以是加密的，也可以是明文的。

  3. 签名（Signature）：是对标头和有效载荷进行签名之后得到的值，用于验证token的完整性和真实性。签名通常使用私钥进行签名，并使用公钥进行验证。

一个完整的token包含了标头、有效载荷和签名三个部分，它们一起构成了一个安全的令牌，用于进行身份验证和授权。

4.3 token认证流程

  1. 客户端发起登录请求，比如用户输入用户名和密码后登录。

  2. 服务端校验用户名和密码后，将用户** id** 和一些其它信息进行加密，生成 token。

  3. 服务端将token 响应给客户端。

  4. 客户端收到响应后将 token 存储下来。

  5. 下一次发送请求后需要将** token 携带上，比如放在请求头中或者其它地方**。

  6. 服务端 token 校验后，校验通过则正常返回数据。

简易版流程：发送登录请求—生成token，携带用户id等—客户端接收到token之后存储在本地—下一次访问的时候将它存储在headers头中。

总结：三者对比；实际上cookie、session、token三者最终的目的都是一样的：鉴权和认证。

总结下来就是：session是空间换时间，token是时间换空间。
