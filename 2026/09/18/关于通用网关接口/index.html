关于通用网关接口

Created2026-09-18|漏洞复刻知识补充
|Post Views:

概述

通用网关接口（CGI）是定义外部程序如何向Web服务器提供信息的标准。CGI为Apache等Web服务器提供了一种与Perl等编程语言交换数据的机制。

CGI是互联网基础设施中最古老的组件之一。尽管已被更新的替代品所取代，但今天他仍然广泛使用。

Web服务器软件传统上仅限于静态网页提供服务。CGI脚本支持生成动态响应，在收到请求时创建。

标准化HTTP服务器

CGI旨在为编程语言提供一种标准化的方式来访问HTTP服务器信息。任何HTTP服务器可以与任何编程语言配对，前提是他们都遵守CGI规范。

启用CGI的服务器将使用类似一下的过程处理请求：

  1. 收到一个新请求：/example.pl。

  2. Web服务器将example.pl识别可执行的CGI脚本，因此他会调用该脚本。

  3. Perl CGI脚本接收有关请求的所有数据，例如其URL和HTTP标头。

  4. example.pl脚本运行；他的输出将作为HTTP响应传回服务器已进行发射。

上面概述的流程与网络服务器的常规操作形成鲜明对比。/example.pl的基本请求将返回该文件的内容。如果该文件不存在，您将收到404响应。

使用CGI时，请求不需要映射到磁盘上的真实文件。相反，运行用户定义的程序。该程序负责生成要发送给客户端的输出。Web服务器不再关心响应的实际内容。

通过CGI交换信息

通过CGI执行的二进制程序可以访问有关传入HTTP请求的各种数据。这包括URL、标头、查询字符串和HTTP方法，以及远程客户端的IP地址。

服务器软件不需要逐字提供所有数据。CGI规范允许服务器从环境变量中排除标头。这可能是为了省略敏感信息——例如Authorization标头的值——或者在可以使用专用变量访问相同信息的避免冗余。

除了有关请求数据外，CGI兼容服务器还必须指示其自身的各种详细信息。这包括主机服务器软件的名称和版本。脚本可以它他们认为合适的时候使用这些细节。

信息****作为变量从服务器传递到CGI程序。该程序与任何其他环境变量相同的方式访问他们。服务器将程序作为自身的子进程运行，在调用可执行文件之前设置环境变量。

其中有一条数据可能不会作为环境变量处理。（因为他很长）请求主题得到特殊处理。这将通过管道传输到标准输入流中。通过CONTENG_LENGTH环境变量通知脚本有多少数据可用。

脚本处理完成后，CGI脚本向服务器****返回一个HTTP响应。这必须是包含标头和可选正文的完整HTTP响应。该脚本发出对其标准输出流的响应。服务器然后通过HTTP连接将响应发送回给客户端。

总结
总的来说就是客户端发送一个请求，通过CGI接收到这个请求之后调用相关的程序进行执行完成要求。然后就是CGI是将信息作为环境变量传入程序中进行执行，并且可以排除那些在请求中的敏感信息。除了这些，CGI还可以调用服务器自身的一些信息。还有就是CGI在调用程序进行执行的时候服务器是将这个程序作为自身的子进程运行，在调用可执行文件之前会设置环境变量。其中请求中的请求体是不会被用来当做环境变量信息传给程序处理的，因为太长了，他会直接通过管道传输给标准输入流，通过一个叫做CONTENT_LENGTH的变量统计这个请求体有多少数据可用之后传回给CGI调用的程序。脚本处理完成之后，通过CGI返回给服务器一个HTTP响应，这必须包含HTTP的标准也就是完整的HTTP响应，之后服务器会通过HTTP连接返回给客户端一个响应。这就是过去的CGI的处理交换信息的大概流程。

精简版总结

  1. 1.​核心功能​：CGI是一个标准协议/接口，它允许Web服务器（如Apache）在接收到特定请求时，​调用并执行外部程序​（如Perl、Python脚本），并将程序生成的动态内容返回给客户端，而不是简单地返回一个静态文件。

  2. 2.​信息传递方式​：•​环境变量​：服务器将HTTP请求的绝大部分信息（如请求方法REQUEST_METHOD、查询字符串QUERY_STRING、客户端IPREMOTE_ADDR等）通过环境变量传递给CGI程序。•​标准输入 (stdin)​​：​请求体（Body）​​ 因为数据量可能很大，不会放入环境变量，而是通过管道发送到CGI程序的标准输入流中。程序通过读取CONTENT_LENGTH环境变量来知道需要读取多少数据。

  3. 3.​执行方式​：服务器为每一个CGI请求创建一个新的子进程来执行目标程序。这是CGI性能瓶颈的主要原因（即“fork-and-execute”模型）。

  4. 4.​返回响应​：CGI程序将计算结果的完整HTTP响应​（包括状态行、 headers和body）写入其标准输出流 (stdout)​。服务器捕获这个输出，并将其直接发送回客户端。

通过ai总结，可以比较直观的看到他的处理过程就是：接受信息标准——传递方式（环境变量）——执行方式（在服务器上开一个子进程）——响应方式（完整的HTTP格式返回）

题外话：今天的CGI在哪里？

CGI 帮助实现了现代网络。它提供了一种极其简单的方法来使用 90 年代中期的技术构建动态服务器端脚本。网页不再是静态 HTML 文件。

CGI 的简单性帮助它在此后的几十年里经久不衰。 CGI 脚本仍在使用，特别是在基于旧语言的遗留应用程序中。技术并没有停滞不前。 CGI 已被更适合当今网络的更现代的替代方案所取代。

传统的 CGI 会产生开销，这在规模上会成为问题。 CGI 脚本会在每次请求时重新加载，产生一个新进程，这会耗尽高流量站点的资源。

CGI 在提供给脚本的控制方面也有局限性。脚本只能确定发送回客户端的响应内容。它们无法影响 HTTP 交换的任何其他部分，例如身份验证或会话管理。

最后，还有安全问题。 CGI 脚本通常作为服务器的子进程执行。这意味着必须保护服务器免受脚本干扰。错误配置可能使脚本无法访问服务器管理的其他资源，例如其配置和日志文件。

CGI 的许多问题已通过较新的接口技术得到解决。创建 FastCGI 是为了减少 CGI 开销问题。它的工作方式与 CGI 类似，但不会为每个请求生成一个新进程。相反，FastCGI 服务器独立于 Web 服务器工作，维护它自己的一组用于托管 CGI 脚本的持久进程。

在其他地方，各个编程语言已经实现了自己的服务器接口。这些通常通过可选模块直接集成到 Web 服务器中。一个例子是 Apache 的 mod_php 和 mod_perl，它们在不使用 CGI 的情况下为这些编程语言提供本地支持（即使两者都可以通过 CGI 使用）。

尽管出现了这些机制，但 CGI 仍然具有相关性。其设计核心的简单性已经为大多数后续改进整体架构的努力提供了信息。虽然您不太可能在现代 Web 系统中每天遇到 CGI，但主要的 Web 服务器继续支持它并且看起来不太可能很快改变。

也就是说如果CGI来到今天使用的话其实缺点也显而易见：

  1. 每一次处理请求的资源开销

  2. 局限性，只是一个外部程序给web服务器提供信息的标准，不能够实现比如身份验证或者会话管理。

  3. 安全也是问题，每一次处理请求都会在服务器自身创建一个子进程，容易发生安全事故。

现代替补：

  1. FastCGI

  2. Servlet

  3. ……
